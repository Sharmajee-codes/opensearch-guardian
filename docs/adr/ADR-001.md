# ADR-001: Primary Data Plane — Direct OpenSearch Connectivity

**Status:** Accepted
**Date:** 2026-08-19
**Decided by:** Phyllis (T4), reviewed by god

## Context

OpenSearch Guardian must support diverse deployment topologies: bare-metal nodes, VMs, managed cloud offerings, Docker Compose stacks, and Kubernetes clusters. The original question was whether Guardian should route all telemetry through Docker or Kubernetes adapters, or connect directly to OpenSearch.

The SOP explicitly distinguishes between the data plane (monitoring, diagnosis, cost analysis) and the control plane (infrastructure provisioning). Section 3 states: *"Guardian should treat OpenSearch connectivity and infrastructure connectivity as separate capabilities. Every useful installation needs an OpenSearch connection; Docker or Kubernetes access is optional."* Section 14 reiterates: *"Direct OpenSearch connectivity is the primary data plane. Docker and Kubernetes are optional control-plane adapters used only when infrastructure management is requested."*

## Decision

OpenSearch REST API connectivity is the primary, always-required data plane. Docker Engine API and Kubernetes API are optional control-plane adapters, activated only when the user explicitly enables provisioning or scaling. The desktop app connects directly to OpenSearch over HTTPS for all monitoring, Cluster Doctor, and cost-optimizer functionality. Infrastructure adapters are layered on top, not underneath, the monitoring stack.

## Consequences

**Positive:**
- Guardian is useful immediately on any OpenSearch deployment without requiring Docker or Kubernetes.
- Reduces the privilege surface: monitoring never needs infrastructure access.
- Keeps the architecture decoupled from deployment topology.
- Matches the official OpenSearch API design (Cluster Health, Nodes Stats, Cluster Stats APIs are the authoritative source).

**Negative:**
- Provisioning workflows require a second connection (Docker or Kubernetes) in addition to OpenSearch.
- Users on managed OpenSearch (e.g., AWS OpenSearch Service) cannot use provisioning features.
- The app must manage two distinct connection profiles per cluster when both monitoring and provisioning are active.

**Mitigations:**
- Connection profiles are discovered and tested independently (SOP §3.1).
- The app UI guides users to enable provisioning only when Docker/K8s access is available.
- The `connections/` module abstracts both transport types behind a common interface.
