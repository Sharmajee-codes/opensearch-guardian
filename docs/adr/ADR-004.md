# ADR-004: Evidence-First Deterministic Cluster Doctor

**Status:** Accepted
**Date:** 2026-08-19
**Decided by:** Phyllis (T4), reviewed by god

## Context

The Cluster Doctor is the core diagnostic engine of OpenSearch Guardian. It must produce trustworthy, auditable diagnoses that operators can rely on before taking action. The risk is that an LLM-based diagnostic could fabricate findings, misinterpret metrics, or recommend unsafe actions without evidence. The SOP requires that diagnosis be evidence-first and deterministic, with LLMs playing a secondary explanatory role only.

## Decision

The Cluster Doctor processes data through a fixed pipeline:

1. **OpenSearch APIs** → raw metrics and status
2. **Normalized facts** → version-agnostic internal models (SOP §4.2)
3. **Deterministic rules** → rule-ID-tagged findings with severity, confidence, and evidence
4. **Correlated findings** → cross-rule synthesis (e.g., disk watermark + unassigned shards → allocation failure cascade)
5. **Confidence / severity scores** → computed from rule certainty and evidence strength
6. **Recommendation** → action guidance classified as Informational, Safe/Reversible, Approval Required, or Destructive (SOP §8)
7. **Optional AI explanation** → LLM summarizes and correlates established findings; never introduces new facts

Each finding contains: rule ID, entity, observed value, threshold/context, severity, evidence citations, confidence score, remediation guidance, and required safety level. LLMs are confined to the final explanation layer and must never be the source of truth for health status, thresholds, or safety assessments. No finding is marked resolved until a subsequent snapshot verifies the expected improvement (SOP §5).

## Consequences

**Positive:**
- Diagnoses are auditable: every finding traces back to a specific API response and rule.
- Operators can trust the Doctor because LLMs cannot hallucinate findings into existence.
- Rule definitions are public and testable (SOP §9), enabling community audit.
- Incident response is faster because findings are structured, not narrative.

**Negative:**
- Rule maintenance requires domain expertise; new OpenSearch features may outpace rule updates.
- The deterministic pipeline is more engineering effort than a pure LLM approach.
- Correlation logic can become complex as rule families grow.

**Mitigations:**
- Rules live in the `rules/` directory as data+code, not embedded in the core.
- Fixtures (SOP §9) provide known-good and known-broken cluster states for rule regression testing.
- The LLM layer is optional and clearly labeled as explanatory, not diagnostic.
