# ADR-007: Open-Source Strategy

**Status:** Accepted
**Date:** 2026-08-19
**Decided by:** Phyllis (T4), reviewed by god

## Context

OpenSearch Guardian must be genuinely useful as an open-source project: a contributor should be able to clone the repository, build the desktop app and core service, connect to a local OpenSearch cluster, and use the core Doctor and cost optimizer without purchasing any service. The SOP emphasizes Apache-2.0 licensing, no mandatory telemetry, plugin/provider extension points, and full transparency of rule definitions and test fixtures.

## Decision

The project adopts the following open-source stance:

- **License:** Apache License 2.0, aligned with OpenSearch's own license. A dependency/license review is performed before the first public release.
- **No mandatory backend:** Core functionality (monitoring, Doctor, cost optimizer) works entirely offline against a local or network-accessible OpenSearch cluster. No proprietary cloud service, paid API, telemetry collector, or hosted backend is required.
- **No mandatory telemetry:** If optional anonymous telemetry is added in the future, it must be opt-in and its schema must be fully documented.
- **Plugin/provider extension points:** Authentication adapters, LLM providers, cost models, Docker/K8s provisioners, exporters, and diagnostic rules are all pluggable interfaces. The core ships with reference implementations; third parties can contribute alternatives.
- **Public rule definitions:** All Doctor rules are stored as public files in the `rules/` directory. Their logic and thresholds are auditable by any operator.
- **Test fixtures:** The `fixtures/` directory contains reproducible healthy and broken OpenSearch cluster states for regression testing.
- **Developer environment:** A `deploy/docker/compose` setup provides reproducible local clusters (healthy and broken) for development and testing.
- **Governance documentation:** LICENSE, NOTICE, CONTRIBUTING.md, CODE_OF_CONDUCT.md, SECURITY.md, SUPPORT.md, and GOVERNANCE.md at the repository root.
- **Signed releases:** Releases include checksums, an SBOM, dependency scanning results, and secret scanning results.
- **Trademark compliance:** Guardian is compatible with OpenSearch but is not an official OpenSearch project; OpenSearch trademark rules are respected.

## Consequences

**Positive:**
- Contributors can participate without proprietary account dependencies.
- Operators can audit every diagnostic rule and cost recommendation.
- The plugin architecture allows the project to evolve without core monolithic growth.
- Apache-2.0 compatibility with OpenSearch encourages adoption by the existing ecosystem.
- Transparent governance builds community trust.

**Negative:**
- No hosted backend means no centralized telemetry to guide prioritization; the community must self-organize feature requests.
- Plugin diversity can lead to quality variance; a review process for third-party providers is needed.
- Apache-2.0 allows proprietary forks; the project relies on community contribution, not license restriction, for vitality.
- Trademark compliance requires ongoing legal awareness.

**Mitigations:**
- A clear CONTRIBUTING.md and CODE_OF_CONDUCT.md lower the barrier for new contributors.
- The GOVERNANCE.md defines how plugin proposals are reviewed and merged.
- The SECURITY.md defines the responsible disclosure process.
- The roadmap (SOP §11) provides transparent prioritization instead of centralized telemetry.
