# ADR-006: Provisioning State Machine

**Status:** Accepted
**Date:** 2026-08-19
**Decided by:** Phyllis (T4), reviewed by god

## Context

Node provisioning and scaling are the most operationally risky features of OpenSearch Guardian. An incorrect node addition can cause shard allocation failures, disk pressure, or cluster instability. The SOP defines a 12-step provisioning workflow (SOP §7) that must be strictly enforced with explicit user approval before any infrastructure mutation. The state machine must make the current stage, allowed transitions, and required evidence visible at all times.

## Decision

Provisioning follows a strict linear state machine with 12 stages:

1. **Discover** — Identify deployment type and authoritative manager (Docker/Compose, OpenSearch Operator, Helm/StatefulSet, or external).
2. **Snapshot** — Capture cluster health, nodes, shards, disk, JVM, versions, settings, and deployment metadata.
3. **Plan** — Calculate requested/Guardian-recommended role, count, CPU, memory, heap, storage, version, and expected impact.
4. **Preflight** — Validate credentials, permissions, version compatibility, network/discovery, storage, capacity, security material, and dependencies.
5. **Review** — Display exact desired-state change, risks, estimated rebalance impact, and rollback/recovery approach.
6. **Approve** — Require explicit user approval for infrastructure writes.
7. **Apply** — Modify the authoritative deployment manager only (Docker Compose file, K8s operator CR, or StatefulSet).
8. **Observe** — Track container/pod startup and controller reconciliation.
9. **Verify join** — Confirm the new node appears through OpenSearch and has the expected roles/version.
10. **Rebalance** — Monitor initializing/relocating/unassigned shards and recovery pressure.
11. **Validate** — Compare before/after health, disk distribution, shard density, JVM/CPU pressure, and failures.
12. **Audit** — Persist who/what/when, requested change, actual change, result, and verification evidence.

Transitions are单向 (forward) with explicit rollback support from Validate back to Snapshot. The Audit stage is mandatory; no provisioning completes without an immutable audit log entry. The state machine is implemented in `guardian/provisioning/` with separate adapters in `guardian/provisioning/docker/` and `guardian/provisioning/kubernetes/`.

## Consequences

**Positive:**
- Every provisioning action is preceded by validation and explicit approval, preventing accidental cluster changes.
- The before/after comparison (Validate stage) provides objective proof that the change succeeded.
- Immutable audit logs support compliance and post-incident review.
- Separate adapters keep Docker and Kubernetes logic isolated.

**Negative:**
- The 12-step flow is longer than ad-hoc provisioning, increasing time to completion.
- Rollback requires a second full provisioning cycle in reverse, which is non-trivial.
- Some deployment types (e.g., external managed clusters) may not support all stages.

**Mitigations:**
- The UI shows a progress indicator with the current stage and remaining steps.
- Preflight (step 4) catches most failures before Apply, reducing wasted effort.
- Stages that don't apply to a deployment type are skipped with a clear explanation, not silently omitted.
