# ADR-009: Kubernetes Control-Plane Adapter

**Status:** Proposed
**Date:** 2026-08-19
**Decided by:** Kevin (T11), to be reviewed by meredith-msyn94lj

## Context

OpenSearch Guardian must support provisioning and scaling for OpenSearch clusters deployed on Kubernetes. The SOP (§3.3) mandates that Guardian work with the cluster's existing deployment controller — patching the OpenSearch custom resource and letting the Operator reconcile — rather than creating unmanaged pods. This decision record formalizes the K8s adapter architecture, credential model, RBAC scoping, and verification loop.

Related decisions:
- **ADR-001** (Primary Data Plane) — K8s is an optional control-plane adapter, not the monitoring path
- **ADR-002** (Read-Only by Default) — Provisioning RBAC is gated separately from monitoring RBAC
- **ADR-006** (Provisioning State Machine) — K8s provisioning follows the 12-step flow, with steps 8–11 adapted for watch/verify

## Decision

Guardian interacts with Kubernetes clusters through a **two-tier adapter model**:

### Tier 1: OpenSearch Operator (Primary Path)

Guardian detects whether an `OpenSearchCluster` custom resource exists in the target namespace. If present, Guardian:

1. Reads the current CR spec and computes a desired-state diff
2. Shows the diff to the user with impact estimation (rebalance time, disk growth)
3. Upon explicit approval, patches the CR via the Kubernetes API
4. Watches the CR status and Pod readiness via Kubernetes watches (5s poll)
5. Switches verification to OpenSearch REST APIs (`_nodes`, `_cluster/health`, `_cat/shards`)
6. Logs the change in the immutable audit trail

Guardian **never** creates or manages OpenSearch Pods directly when an Operator is present.

### Tier 2: Helm / StatefulSet Fallback

If no `OpenSearchCluster` CR is found, Guardian detects the deployment type:

- **Helm-managed:** Guardian reads the Helm release values, computes a diff, and applies via `helm upgrade --dry-run` for review, then `helm upgrade` after approval.
- **Raw StatefulSet:** Guardian patches the `replicas` field of the StatefulSet directly, with stricter preflight validation (no Operator to catch misconfigurations).

### Credential Model

- **Primary:** User's local kubeconfig context. Guardian stores only the context name; credentials are read from the kubeconfig file at runtime and never persisted in plaintext.
- **Secondary:** In-cluster service account token, used only when Guardian runs inside the cluster and the user explicitly consents.
- All credential handling stores secrets in the OS keychain, never in project configuration files (per SOP §8).

### RBAC Scoping

Monitoring and provisioning RBAC are **separate Roles** bound to separate ServiceAccounts:

- **Monitoring Role:** `get`, `list`, `watch` on Pods, Services, PVCs, StatefulSets, and `OpenSearchCluster` resources. No write verbs.
- **Provisioning Role:** `patch` on `OpenSearchCluster` and StatefulSet resources. No `delete` verbs. No access to secrets or configmaps beyond what is needed for the CR.

At connection time, Guardian tests both roles independently and reports their status in the connection profile.

### Watch/Reconcile/Verify Loop

After applying a CR/StatefulSet patch:

1. **Watch K8s** (5s interval): Monitor CR `status.conditions` for `Ready` and Pod `status.phase` for `Running`
2. **Timeout threshold:** 5 minutes — after which Guardian surfaces a warning and suggests manual investigation
3. **Verify via OpenSearch:** Confirm node appears in `_nodes`, cluster health is acceptable, shard allocation is progressing
4. **Audit:** Record the patch request, the applied diff, the verification evidence, and the final cluster state

### Dry-Run and Approval

Per the provisioning state machine (ADR-006, steps 5–6):

- Guardian performs a client-side dry-run of the patch before any API call
- The diff is displayed in the UI with risk annotations (disk growth estimate, rebalance time)
- Explicit user approval is required before the patch is sent to the K8s API
- A rollback plan is shown (revert to previous CR spec or StatefulSet replicas)

## Consequences

### Positive

- **Operator-compliant:** Guardian respects the Operator's reconciliation loop, avoiding conflicts with other controllers.
- **Safe by default:** Monitoring RBAC is read-only; provisioning requires explicit approval and scoped permissions.
- **Fallback coverage:** Helm and raw StatefulSet paths ensure Guardian works even without the Operator installed.
- **Evidence-based verification:** The switch from K8s watches to OpenSearch API verification ensures the cluster itself confirms the change, not just the K8s layer.
- **Audit trail:** Every change is logged with before/after state, satisfying compliance requirements.

### Negative

- **Operator dependency:** The primary path requires the OpenSearch Kubernetes Operator to be installed. Clusters without it fall back to less-validated paths.
- **Credential complexity:** Managing kubeconfig contexts and in-cluster credentials adds friction to the connection setup flow.
- **Watch latency:** The 5-second poll interval introduces delay between patch and verification; fast incident response may feel sluggish.
- **Helm limitations:** Helm upgrades are less granular than CR patches; rolling back requires helm history management.

### Mitigations

- **Operator detection:** Guardian clearly reports whether the Operator is present and which fallback path is active.
- **Connection test:** The connection profile setup validates both monitoring and provisioning RBAC independently, giving clear feedback before the user attempts provisioning.
- **Adaptive polling:** During active provisioning, Guardian increases watch frequency (1s) and falls back to 5s once stable.
- **Helm version pinning:** Guardian records the Helm chart version in the audit log to aid rollback.
